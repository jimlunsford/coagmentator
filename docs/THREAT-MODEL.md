# Threat Model

Gate 1 design candidate, 2026-10-05. Assets: editorial integrity, unpublished/private content, credentials, site availability, media/files, operation provenance and operator control. Adversaries include unauthenticated callers, holders of stolen credentials, malicious content authors, prompt-injected clients and compromised service components. The AI client and all content are untrusted. WordPress core, installed PHP/plugins, database and the host form one trusted execution domain; compromising it defeats bridge controls.

Controls below are **requirements for later implementation**, not claims of protection already deployed. The authoritative controls are in [SECURITY.md](SECURITY.md), [AUTHENTICATION.md](AUTHENTICATION.md), [CAPABILITIES.md](CAPABILITIES.md) and [CONTRACTS.md](CONTRACTS.md). Each threat links to a verification obligation; Gate 1 reviews the design, later gates execute the tests.

## Scenarios

| --- | --- | --- | --- | --- |
| T01 Stolen MCP access/refresh credential | Attacker calls valid tools as the authorized operator | Draft/private disclosure, permitted edits, approval spam | Five-minute access lifetime, rotating refresh tokens, subject/client consent, exact audience, scopes, local disable, limits; bridge approvals for public/destructive effects | A valid stolen token can read and perform enabled low-impact writes until revoked/expired. Gate 4 tests expiry/revocation and scope boundaries |
| T02 Stolen WordPress credential | Attacker bypasses MCP and calls native REST, XML-RPC, user self-edit or bridge directly | Bypass OAuth restrictions; misuse native editing privileges | Dedicated least-privilege user; must-use route guard; approved credential UUID; no XML-RPC/batch/alternate paths; bridge independent approvals and rate limits | Low-impact bridge operations remain available within service privileges. Removing all guard code while credential is active reopens native API reach. Gates 2/5 test direct and encoded/nested bypass attempts |
| T03 Prompt-driven misuse of valid tools | User/content persuades AI to make a schema-valid harmful request | Unwanted drafts, edits, term creation or publication | Narrow schemas, write families off by default, explicit publish/Trash operations, no generic runners, native/custom capabilities, exact-intent approvals | Standing authorization still permits low-impact misuse. No intent classifier can guarantee benevolence. Gate 3 tests harmful but schema-valid requests against policy |
| T04 Malicious post or revision instructions | Retrieved content says to reveal secrets, switch sites or approve a write | Tool misuse or data exfiltration | Treat raw text as data; no dynamic tool descriptions from content; no credential-return tool; no arbitrary URL/path inputs; independent approval | Client may disclose authorized content to other tools outside Coagmentator. | T05 Privilege escalation | Caller supplies author, status, role, arbitrary meta key, private status or generic ability name | Broader WordPress control, persistent content injection | Closed schemas, fixed authorship/type/status transitions, exact meta keys, forbidden native grants, per-object `current_user_can` | Trusted plugins can change WordPress capability mappings; test configured deployment, not role labels. Gate 2 negative capability matrix |
| T06 Confused deputy / account substitution | Valid issuer user changes site/actor/target URL or client passes a token for another audience | Unrelated user/site modified using service credentials | One pinned `(issuer, subject)` and site/actor binding; tool cannot choose identity/URL; audience validation; explicit provider consent; no token passthrough | Compromised MCP can impersonate its configured operator but remains inside bridge ceiling. Gate 4 wrong-subject/audience/site tests |
| T07 Replay of a recorded mutation | Exact request resent after success, expiry or credential rotation | Repeated publish/upload/create | Durable actor/site-scoped key, request hash, timestamps, 90-day retention and expiry rejection, current authorization on replay | New key or changed timestamp after retention is new intent, not detectable replay. | T09 Forged mutation receipt | Fake HTTP success, wrong-site response, altered IDs, hostile proxy or compromised server | Client believes an unperformed or different change occurred | Verified TLS, bound receipt schema/IDs, fresh WordPress readback, bridge-owned journal, independently accessible operator record | No cryptographic non-repudiation; compromised bridge can forge evidence, compromised MCP can lie to client. Gates 2/4 seeded-secret redaction checks |

| T15 Oversized payloads | Huge raw body, base64, result list, deeply nested JSON or image dimensions | Memory/CPU/disk exhaustion | Byte limits before parse/decode, max JSON depth 20, fixed schemas, limits/cursors, bounded image workers, deadlines and disk quota | Many small requests still consume work. | T16 DoS / approval or journal flooding | Valid/invalid callers exhaust workers, journal, log storage or review queue | Availability loss, operator fatigue | Pre-auth and authenticated rate limits, concurrency caps, 20 pending approvals/binding, 10,000 journal records/binding, 100 MiB pending-payload quota, fail closed at quota, bounded retention | A valid token can temporarily exhaust its allowance; host-wide volumetric DoS needs infrastructure controls. | T18 Compromised MCP server | Host attacker steals Application Password, lies about actor, rewrites results | Low-impact edits/disclosure and deceptive client results | Least-privilege WP identity, must-use guard, bridge-side operation policies, exact approval records inaccessible to service identity, operator kill switch | Readable content and enabled low-impact writes are exposed; an already approved exact action can be executed. | T19 Compromised WordPress/site/DB | Plugin or host attacker modifies capabilities, files, state or journal | All site content and receipt integrity lost | Patch/support matrix, narrow deployment permissions, backup/restore and independent incident records | No bridge design can attest truth from a compromised WordPress trust domain. | T20 Man-in-the-middle / credential forwarding | Bad cert, HTTP downgrade, forged proxy headers, cross-host redirect | Credentials/content intercepted or tool results altered | TLS hostname/chain validation, no downgrade/redirect, trusted-proxy configuration, canonical origins, no token passthrough | Compromised trusted CA/proxy/host remains trusted-path risk. Gates 2/4 failed-TLS/header-spoof tests |
| T21 Accidental publication | Generic update status or stale approval exposes draft | Unreviewed public content, irreversible syndication/email | Draft-only creation, dedicated publish tool, fresh version, exact approval, current scopes/caps, publish time set explicitly | Approved publication can trigger external hooks and cannot be reliably recalled. Gate 3 verifies no alternate status path |
| T22 Accidental destructive change | Trash disabled, empty taxonomy array, broad revision restore, partial multi-field write | Permanent deletion or unexpected content rollback | Refuse disabled Trash; no hard-delete tools; nonempty categories; restore only selected editorial fields; preserve status/meta; prevalidate all fields, report partial failures | Native Trash auto-empty still deletes later; hooks can change data. Operator sees retention and keeps backups. Gate 3 disabled-Trash and restore-preservation tests |
| T23 Future cross-site confusion | Same IDs, copied databases, changed URLs or cached cursor/approval reused elsewhere | Wrong site read or changed | Random pinned site ID in every envelope/hash/approval/journal key, no site switch input, separate site identity on clone, audience/site binding | An operator copying identity and credentials verbatim can defeat this. Gate 5 copied-ID/misrouting tests; multisite needs a new design |
| T24 Concurrent native edits | WordPress editor/plugin writes between version check and bridge write | Lost update or misleading final snapshot | Fresh full projection, bridge locks, respect core editor locks, immediate precheck/readback; controlled editing window for live writes | Core does not honor bridge locks; final-window races can escape detection. Explicitly no global CAS guarantee. Gate 3 documents and simulates the race |
| T25 Approval substitution / stored XSS | MCP changes arguments after approval or malicious diff executes in admin browser | Different operation or theft of human session | Approval binds complete intent/preconditions/site/actor/policy; escaped text diff, sanitized raster preview, no embedded raw HTML, frame restrictions, service-user exclusion | Human can approve a harmful exact proposal; UI correctness is essential. Gate 3 changed-byte and hostile-preview tests |
| T26 OAuth mix-up / malicious registration | Attacker swaps issuer/callback/CIMD URI or uses open DCR | Code/token theft, SSRF or wrong-account link | Established provider, fixed issuer, PKCE S256, RFC 9207, exact callbacks, pre-registration baseline, CIMD allowlist, no DCR in MVP | Provider misconfiguration or compromise remains possible. ## Trust boundaries and control ownership

The client controls tool arguments but cannot set bridge URLs, credentials, role grants, approval decisions, policy versions or server-generated receipts. MCP owns OAuth validation and client scopes. The bridge owns WordPress authorization and mutation truth. The human approval browser is a separate cookie/CSRF boundary. Authorization-provider metadata and upload bytes are input boundaries even when transmitted over HTTPS. WordPress owns its database/files and executes installed PHP; the MCP host has no database credentials or WordPress filesystem mount.

Source principles: [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) identifies token passthrough, confused-deputy, OAuth discovery/registration and state-handle risks. The concrete scenarios, controls, residual risks and test assignments here are Coagmentator's analysis, not an audit certification.

## Gate acceptance implications

Gate 1 is design-ready only when every mitigation has a permanent contract/architecture owner and an objective later verification gate. No currently unresolved security mechanism is hidden as "TBD". Known limits are explicit: native concurrent writers, compromised trusted components, public uploads, WordPress hook side effects, Trash retention, limited content formats, client file transfer, and opt-in basic SEO rather than vendor compatibility. Human review must accept these limits or require a contract revision before Gate 2. No implementation acceptance or production security claim follows from accepting this document.
