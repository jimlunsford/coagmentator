# Threat Model

Accepted Gate 1 design, 2026-10-05. Assets: editorial integrity, unpublished/private content, credentials, site availability, media/files, operation provenance and operator control. Adversaries include unauthenticated callers, holders of stolen credentials, malicious content authors, prompt-injected clients and compromised service components. The AI client and all content are untrusted. WordPress core, installed PHP/plugins, database and the host form one trusted execution domain; compromising it defeats bridge controls.

Controls below are **requirements for later implementation**, not claims of protection already deployed. The authoritative controls are in [SECURITY.md](SECURITY.md), [AUTHENTICATION.md](AUTHENTICATION.md), [CAPABILITIES.md](CAPABILITIES.md) and [CONTRACTS.md](CONTRACTS.md). Each threat links to a verification obligation; Gate 1 reviews the design, later gates execute the tests.

## Scenarios

| T01 Stolen MCP access/refresh credential | Attacker calls valid tools as the authorized operator | Draft/private disclosure, permitted edits, approval spam | Five-minute access lifetime, rotating refresh tokens, subject/client consent, exact audience, scopes, local disable, limits; strict approvals for designated effects; trusted profile retains every scope/capability/enablement check | A stolen token can exercise its enabled/scoped trusted-policy writes until revoked/expired, including high-impact families; strict requires separate approval for designated writes. | T02 Stolen WordPress credential | Attacker bypasses MCP and calls native REST, XML-RPC, user self-edit or bridge directly | Bypass OAuth restrictions; misuse native editing privileges | Dedicated least-privilege user; must-use route guard; approved credential UUID; no XML-RPC/batch/alternate paths; bridge approval-profile enforcement and rate limits | All enabled trusted-profile bridge operations remain available within service privileges; strict high-impact operations still need independent approval. ## Trust boundaries and control ownership

The client controls tool arguments but cannot set bridge URLs, credentials, role grants, approval decisions, policy versions or server-generated receipts. MCP owns OAuth validation and client scopes. The bridge owns WordPress authorization and mutation truth. The strict human approval browser is a separate cookie/CSRF boundary; trusted policy deliberately omits that second approval while retaining all server checks. Authorization-provider metadata, forged client-file locators and upload bytes are input boundaries even over HTTPS. File schema/metadata do not attest provenance. MCP owns the restricted file retrieval, generated request IDs/timestamps and model evidence projection; the WordPress bridge never retrieves a file URL. WordPress owns its database/files and executes installed PHP; the MCP host has no database credentials or WordPress filesystem mount.

Source principles: [MCP security guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices) identifies token passthrough, confused-deputy, OAuth discovery/registration and state-handle risks. The concrete scenarios, controls, residual risks and test assignments here are Coagmentator's analysis, not an audit certification.

## Gate acceptance implications

Gate 1 is design-ready only when every mitigation has a permanent contract/architecture owner and an objective later verification gate. No currently unresolved security mechanism is hidden as "TBD". Known limits are explicit: native concurrent writers, compromised trusted components, trusted-profile compromised-MCP authority, public uploads, WordPress hook side effects, Trash retention, limited content formats, client file transfer, and opt-in basic SEO rather than vendor compatibility. Human review accepted these limits with the exact Gate 1 candidate recorded in ROADMAP.md. No implementation acceptance or production security claim follows from accepting this document.
